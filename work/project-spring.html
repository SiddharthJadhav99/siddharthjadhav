Context

Before Project Spring, equipping a new hire meant manual tickets, guesswork about which laptop or peripherals the role needed, and days of back-and-forth with IT.

The agent replaces that with one guided conversation. It:

  • collects six details about the new hire, including role, department, location and start date
  • looks up what similar employees on the same team actually use in ServiceNow
  • recommends equipment, falling back from peer data to a role map to a sensible default
  • gets the manager’s approval in chat or by email through Microsoft Graph
  • places real ServiceNow catalog orders and returns the request numbers

The whole flow takes about two to three minutes and ends with orders placed, grounded in real data rather than a generic checklist.

The problem with the first version

The proof of concept used five LLM agents with an LLM orchestrator deciding who should act next. It demoed well and behaved unpredictably:

  • the orchestrator sometimes routed to the wrong agent or invented a handoff
  • the approval agent occasionally reported an approval the manager never gave, or ended the session early when someone changed an item
  • every step paid for an extra LLM round trip just to decide what came next, so runs were slow and costly

None of these were prompt problems. They came from letting a model make decisions that had a single correct answer.

What I built

I replaced the dynamic handoffs with a fixed workflow graph in Microsoft Agent Framework:

  • Two LLM agents, used only where a human is in the conversation: one collects the new hire’s details, one handles approval.
  • Four code steps for the ServiceNow lookup, the recommendation, the ordering and the summary. They run in seconds, can be unit tested, and can’t hallucinate.
  • A code router that reads workflow state, so choosing the next step costs zero LLM calls.
  • Typed outputs with Pydantic. The approval agent returns a structured decision, and only an explicit approval can reach the ordering step. A rejection ends the run before any ticket exists.
  • A fresh workflow per session, so one manager’s conversation can never leak into another’s.

Finding the right equipment

A new hire doesn’t exist in ServiceNow yet, so I pivoted the lookup to the hiring manager’s team. The lookup chains four steps: manager, then teammates with a similar job code, then the assets they hold, then the orderable catalog item for each model. Only active catalog items are considered, which stopped orders failing on retired hardware.

Governance and security

I designed the AI governance layer so policy lives outside the agents, where a model can’t argue its way past it:

  • all model traffic goes through Azure API Management, which applies content moderation and checks on both input and output
  • Open Policy Agent makes the policy decisions, and each agent carries its own identity so rules can differ per agent
  • private networking, managed identity and least-privilege role assignments, all defined in Bicep
  • OpenTelemetry traces tied to each session, giving an end-to-end audit trail

I also wrote the governance implementation plan: a zero-trust design split into six phases that can each ship on their own.

Hard problems

An agent that approved things nobody approved

Stricter prompt rules reduced it but didn’t remove it. Moving to a typed decision, with approval as the only path into ordering, removed the failure by construction.

Data that stores references, not names

ServiceNow links users, assets, models and catalog items by reference. The four-step lookup resolves those references into items that can actually be ordered.

Corporate network quirks

Traffic inspection on the corporate network broke TLS for the model client, so I added a custom certificate setup. A gateway URL quirk in the SDK needed a fix of its own.

Deploys that broke after server reboots

The container runtime on the shared deploy server kept stale state after reboots, so I added a CI job that detects and repairs it automatically.

Teammates built the ServiceNow ordering APIs, single sign-on, email approvals, the evaluation suites and the telemetry exporters. The design described here, the lookup logic, the performance overhaul, the infrastructure and the governance work were mine.

What’s next

The pattern, a fixed workflow for business steps and a governed gateway for every model call, is set up to become the template for future Hershey agents, such as incident workflows and asset questions, under a larger multi-agent workflow.
